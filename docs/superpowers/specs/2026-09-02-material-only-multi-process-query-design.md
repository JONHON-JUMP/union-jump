# 仅物料号查询多组工艺设计

## 目标

扩展 MES 工艺卡 `queryCard`：在保留现有正式工艺和指定临时工艺查询方式的基础上，允许用户仅输入物料号。后端调用临时工艺接口后按 `ROUTREMARK` 分组，将正式工艺组和临时工艺组分别按既有流程构造成多张工艺卡，前端一次展示全部有效结果。

## 查询模式与校验

查询条件支持三种模式：

| 模式 | 物料号 `prtno` | 工艺规程号 `accno` | 处理方式 |
| --- | --- | --- | --- |
| 正式工艺 | 可空 | `C` 开头 | 复用现有正式工艺流程 |
| 指定临时工艺 | 必填 | 非空且非 `C` 开头 | 复用现有临时工艺流程 |
| 物料下全部工艺 | 必填 | 空 | 调临时接口、分组并返回多张工艺卡 |

物料号和工艺规程号不能同时为空。输入非 `C` 工艺规程号时，物料号仍然必填。前端提供即时表单校验，后端同时保留防御性校验，避免绕过页面直接调用接口产生空指针或无效请求。

## 后端架构

`ProcessServiceImpl.queryCard` 作为统一编排入口，先规范化输入并判断查询模式：

1. `accno` 以 `C` 开头时，返回现有正式工艺卡。
2. `accno` 非空且不以 `C` 开头时，按现有指定临时工艺逻辑查询。
3. `accno` 为空、`prtno` 非空时，进入物料下全部工艺查询。
4. 其他非法组合返回明确参数错误。

正式工艺构造逻辑从“直接返回单元素列表”收敛为可复用的单卡构造方法，供直接正式查询和物料分组查询共同调用。现有正式工艺的版本接口、发行状态校验、树构造及工艺文件行为不变。

指定临时工艺逻辑同样保留现有行为，包括返修判断、`plndept` 计算、文档号获取、发行校验和临时工艺树构造，避免本次多组能力影响原有调用方。

## 仅物料号请求与分组

仅输入物料号时，临时工艺接口请求体固定包含四个字段：

```json
{
  "prtno": "用户输入的物料号",
  "plndept": "",
  "accno": "",
  "fxtype": "0"
}
```

响应校验继续复用现有临时接口信封解析规则。取得 `details` 后按每条明细的 `ROUTREMARK` 分组：

- 分组键先去除首尾空白。
- `ROUTREMARK` 为空的明细直接跳过。
- 以 `C` 开头的分组视为正式工艺，分组键作为正式工艺规程号；临时接口明细不参与正式工艺树构造。
- 其他分组视为临时工艺，只使用本组明细构造该组的工艺树。

返回顺序固定为：正式工艺组在前，临时工艺组在后；每一类内部按 `ROUTREMARK` 字符串升序排列。该顺序由后端保证，前端不再次重排。

## 分组卡片构造

### 正式工艺组

每个正式工艺组用 `ROUTREMARK` 调用现有正式流程：查询版本、截取第一个点号前的主版本、检查 `CAOE_PP.pp_state`、递归查询正式工序并构造工艺树。卡片字段和现有正式查询保持一致。

### 临时工艺组

每个临时工艺组以 `ROUTREMARK` 查询 `CAOE_DOC` 最新版本：

- 文档必须存在且状态为“已发行”。
- 文档 OID 必须存在。
- 仅将该组的 `details` 交给 `TemporaryProcessTreeAssembler`，继续按 `Seqno` 数值层级排序和组树。
- 卡片 `accno` 使用该组的 `ROUTREMARK`。
- `version` 为空、`isFormal` 为 `0`、`isFix` 为 `0`。
- 每个工序 URL 使用该组文档 OID 拼接，不能复用响应体顶层 OID。

## 部分成功与异常策略

多组查询采用部分成功策略。单个分组因未发行、文档缺失、OID 缺失、正式工艺版本查询失败或其他可预期业务异常而失败时：

- 后端记录包含 `ROUTREMARK` 和失败原因的告警日志。
- 跳过该组，继续处理其他分组。
- 响应暂不新增失败明细字段，前端只展示成功卡片。

若所有分组均为空或处理失败，统一返回“未查询到有效工艺信息”。临时接口本身调用失败、响应信封非法或 `details` 不是有效数组时，仍按现有接口级错误处理，不进入分组级容错。

## 前端设计

Vue 2 页面继续使用现有 `queryCard` API 和数组响应结构，不增加新接口。

表单规则调整为：

- 两个输入框至少填写一个。
- `accno` 以 `C` 开头时允许不填物料号。
- `accno` 非空且非 `C` 开头时要求物料号。
- 只填物料号时允许提交，并发送物料号和空 `accno`。
- 任一字段变化时重新校验关联字段，及时清除过期错误。

现有 `normalizeCards` 已支持多卡树形展示，继续把每张卡片作为根节点。页面补充以下多组语义：

- 最近查询在只填物料号时只显示物料号，不产生尾随斜杠。
- 多张卡片时摘要显示工艺组数和汇总工序数。
- 同时存在正式与临时卡片时，类型显示“混合工艺”；全部同类时显示对应类型。
- 展开、收起和工艺文件查看逻辑保持不变。

## 测试策略

后端测试覆盖：

1. 三种合法模式和非法参数组合。
2. 仅物料号请求体四个字段的准确值。
3. 按 `ROUTREMARK` 分组、空值过滤、正式优先及组内升序。
4. 正式组复用正式流程，临时组只使用本组明细和本组文档 OID。
5. 单组失败时其他组仍返回，全部失败时提示“未查询到有效工艺信息”。
6. 指定正式工艺和指定临时工艺的既有行为不回归。

前端测试覆盖：

1. 正式工艺、指定临时工艺和仅物料号三种请求参数。
2. 两项皆空及非 `C` 工艺号缺少物料号的校验。
3. 多卡响应的渲染、混合类型摘要和汇总数量。
4. 仅物料号最近查询文案与回填。
5. 既有并发查询、展开收起和工艺文件查看行为不回归。

完成后运行 MES 模块相关 Maven 测试、前端 Node 测试、前端 lint/build（以仓库已有脚本为准）以及 `git diff --check`。

## 非目标

- 不修改第三方临时工艺、MPM 或 PDM 接口协议。
- 不新增工艺编辑能力。
- 不在本次响应中增加“失败分组详情”字段。
- 不并发调用各分组的外部接口或数据库查询；优先保证顺序、日志和异常隔离清晰。
