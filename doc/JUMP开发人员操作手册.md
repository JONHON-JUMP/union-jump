# 第一部分 系统概述

## 1.1 JUMP 的作用

**现状**：公司的信息化系统是随着业务发展逐个建成的，长期缺少统一规划。生产制造环节，几乎每个车间都独立建设了自己的 MES——仅制造一部 4 个车间就有 4 套 MES，同类系统越建越多；职能管理环节，又陆续上线了通用工装系统、接口平台系统、EAM 系统等全厂级系统。这些系统分属三种技术架构，账号体系与权限模型互不相通：

| 架构 | 代表系统 | 特点 |
|---|---|---|
| Camstar | 各车间 Camstar MES | 外购的 C# 商用系统，闭源不可改造，凭原生 Cookie 会话识别用户 |
| 若依（RuoYi）系 | 各车间若依 MES | 基于若依框架自研，token 鉴权，可改造 |
| 芋道（yudao）系 | 通用工装系统、EAM 系统 | 基于芋道框架自研（JUMP 门户自身也基于该架构），token 鉴权，可改造 |

各系统独立运行多年，逐步积累了三重信息壁垒：

- **账号壁垒**：每套系统一套账号、一个登录入口。员工往往在多套系统中各有一个账号，账号命名还不统一（有的用工号、有的用域账号或自建用户名）；日常使用要先记住各系统的 IP:端口地址，换系统就要重新登录；管理员也难以回答"某个人到底能进哪几个系统、用哪些功能"。
- **人员维护壁垒**：各 MES 在自己的基础数据/车间模型模块中独立维护部门、车间、角色、班组、产线、人员，同一批主数据多处录入、口径不一（车间编码、班组归属在各系统并不完全一致）；员工入职、转岗、离职时必须逐系统增删改账号，漏改、错改时有发生，废弃账号越积越多。
- **入口分散**：员工靠各自收藏的地址进系统，没有统一入口，也无法统一管控"谁能用哪些系统、看哪些菜单"；各系统菜单动辄上百个，界面风格与操作习惯各异，跨车间、跨系统的业务只能在多套系统间反复登录切换。

**目的**：JUMP（Jonhon Unified Management Portal）作为企业统一登录门户，核心做两件事——**统一用户管理、打通信息壁垒**：

- **一处登录，全网通行**：以工号 / 域账号 / 用户名登录门户一次，即可免密码进入所有已接入的业务系统；
- **菜单统一聚合**：各业务系统的页面以免登录方式嵌入门户，统一呈现、统一切换，员工不再记忆各系统地址与账号；
- **人员一处维护，多系统同步**：人员、角色以及角色-菜单的关系统一在 JUMP 维护，经配置的人员接口自动推送到业务系统开通账号；
- **权限统一供给**：JUMP 将各系统的权限上下文（角色、权限点）写入 Redis 权限包，业务系统可直接读取，不重复建设权限模型。

**对不同用户的价值**：

| 用户 | 原来的痛点 | JUMP 带来的改善 |
|---|---|---|
| 车间工人 / 现场操作人员 | 现场电脑多为小尺寸触摸屏，操作不便；角色往往仅授权一小部分菜单，但仍需在原系统庞大的列表式菜单中逐层查找 | 登录后直接进入个人**快捷导航**，常用页面一屏直达，较列表式菜单更易定位 |
| 所有业务系统使用者 | MES 菜单数量庞大且持续增长，列表式菜单查找困难 | 门户按角色仅显示已授权菜单，配合快捷导航与全局搜索，常用页面一步直达 |
| 部门领导 | 一人管理整个部门，部门下多个车间各建一套 MES（如制造一部 4 个车间即有 4 套 MES），需逐一登录、切换系统查看 | 一个入口登录一次，顶部导航即可在多套系统间切换，跨车间业务统一处理 |
| 系统管理员 | 人员账号分散在各系统维护，建号、授权、停用均需逐系统操作 | 人员与角色在门户统一维护，经人员接口推送同步至各业务系统 |

对应到数据职责上的变化：

| 分类 | 旧模式（各车间 MES 自维护） | JUMP 模式（门户统一维护） |
|---|---|---|
| 人员 | 工号、姓名、刷卡号、ERP 账号、OA 账号、角色、主页面、班组、车间、密码、密码永不过期 | 工号、姓名、刷卡号、ERP 账号、域账号、角色（+ 所属主用户、注册状态） |
| 角色 | 角色、页面集合 | 角色、页面集合（菜单权限）在门户维护；不从门户向业务系统推送角色 |
| 部门 / 车间 / 班组 / 产线 | 各 MES 各自维护 | 部门与车间经「车间对照」映射；班组、岗位在门户按系统维护 |

## 1.2 核心概念

本手册涉及以下核心概念：

| 概念 | 说明 |
|---|---|
| 工号 | 全公司统一的用户标识。JUMP 与所有业务系统均以工号识别用户：登录门户使用工号，进入业务系统后，系统同样依据工号确认当前操作人员 |
| 门户账号 | 登录 JUMP 的账号，用户名即工号，同时登记姓名、域账号、刷卡卡号、ERP 账号等身份信息。每位员工仅拥有一个门户账号 |
| 业务系统 | 接入 JUMP 的各信息系统，包括各车间 MES、通用工装系统、EAM 系统等。业务系统仍在原有环境中独立运行，仅访问入口统一收敛至门户 |
| 花名册 | 人员在某一业务系统中的登记信息，包括所属车间、班组、角色，以及进入该系统后的默认主页面。一名人员可同时登记于多个业务系统（即拥有多份花名册），全部关联至其门户账号 |
| 角色 | 一类岗位的权限集合，决定人员可访问的系统范围与可见菜单范围。管理员为花名册分配角色，即完成相应权限的授予 |
| 快捷导航 | 登录门户后首页展示的常用页面入口，可直接打开对应业务页面，便于高频功能的快速访问 |

## 1.3 总体架构

JUMP 的定位是**统一入口、统一管理，不改变业务系统本身**：各业务系统仍在原有服务器上运行，业务功能与数据保持不变，仅将页面访问入口统一收敛至门户。

技术架构：

```
┌─────────────────────────────────────────────────────────────┐
│                        浏览器（用户）                          │
│   登录 JUMP（工号/域账号/用户名） → 写入身份 Cookie               │
└──────────────┬──────────────────────────────────────────────┘
               │ iframe 嵌入（免登录，凭身份 Cookie）
┌──────────────▼──────────────┐  ┌─────────────────────────────┐
│        JUMP 门户（前端）       │  │       业务系统（业务系统）       │
│  菜单聚合 / 系统切换 / 页签管理 │  │  若依系 / 芋道系自研系统       │
├──────────────────────────────┤  │  Camstar 等现成系统          │
│        JUMP 门户（后端）       │  │  （解码 Cookie 识别工号）      │
│  主用户 / 花名册 / 菜单 / 角色  │  └──────────┬──────────────────┘
│  车间对照 / 人员接口配置        │             │ SDK 反向调用（可选）
│  权限包写入 / 业务系统专用端点    │◄────────────┘
├──────────────────────────────┤
│  适配层：HTTP 通用型 / Camstar 会话型 → 调各业务系统人员接口    │
├──────────────────────────────┤
│  PostgreSQL（业务数据）  Redis（权限包 / 菜单缓存 / RBAC 版本）  │
└──────────────────────────────┘
```

系统间职责分工：

| 事项 | 负责方 |
|---|---|
| 人员、角色、菜单权限维护 | 管理员在 JUMP 管理后台统一操作 |
| 人员账号开通至各业务系统 | JUMP 通过各系统提供的人员接口自动推送，或由管理员在门户页面直接操作 |
| 业务功能与业务数据 | 各业务系统自行负责，JUMP 不介入 |
| 当前操作人员识别 | 各业务系统依据工号识别，登录门户时身份已自动传递，无需再次输入账号密码 |

JUMP 对业务系统的三种对接能力：

| 能力 | 方向 | 说明 | 是否必做 |
|---|---|---|---|
| 页面集成（免登录） | 门户 → 业务系统 | 业务系统页面以 iframe 嵌入门户，凭身份 Cookie 免登录访问 | **必做** |
| 人员同步 | 门户 → 业务系统 | 门户创建用户时登记花名册，经 HTTP 接口推送开通账号；支持查询、修改、删除 | 按需 |
| 反向调用 | 业务系统 → 门户 | 业务系统经 SDK 调用 JUMP：机端刷卡校验、权限包读取、扩展缓存读写 | 可选 |

## 1.4 JUMP 与业务系统的边界

职责划分原则：**JUMP 管"人、角色、入口"，业务系统管"事、数据、业务权限"**。

| 职责 | 归属 | 说明 |
|---|---|---|
| 用户身份与登录入口 | JUMP | 主用户、花名册、密码、登录页均在门户；工号是全网唯一标识 |
| 角色 / 菜单 / 权限分配 | JUMP | 角色、菜单、角色-菜单关系、用户-角色关系统一在门户维护并写入 Redis 权限包 |
| 人员账号开通 | JUMP 推送、业务系统落地 | 门户经人员接口推送；业务系统按契约提供接口并落地本系统用户 |
| 业务功能与业务数据 | 业务系统 | 业务页面、业务表、业务流程完全归属业务系统，JUMP 不侵入 |
| 业务内细粒度权限 | 业务系统 | 权限包提供角色与按钮权限点；业务规则级权限（如数据范围）由业务系统自理 |
| 用户识别 | 业务系统 | 业务系统负责解码身份 Cookie 得到工号，并保证工号在本系统可检索到用户 |
| 会话保活 / 页签体验 | 各自负责 | 门户负责 iframe 容器与打开链路；业务系统保证页面可被 iframe 嵌入、接口可凭 Cookie 调用 |

边界上的四条设计原则：

1. **低侵入**：对业务系统改造量最小化。现成系统（如 Camstar）零代码接入；自研系统仅需拦截器与配置级改造；
2. **配置驱动**：人员同步接口以纯配置方式接入（HTTP 通用型适配器），新增同类系统无需门户侧开发；
3. **失败隔离**：门户本地操作（建用户、登记花名册）不依赖外部接口可用性，外部推送显式触发、逐项容错；
4. **可观测**：打开链路诊断、接口在线测试、连通性测试贯穿集成全链路。

# 第二部分 跨系统登录机制

## 2.1 完整登录链路

用户登录 JUMP 一次后进入所有业务系统，全程**没有二次输密码**：

```
用户登录 JUMP（工号 / 域账号 / 用户名 + 密码）
  → 门户前端立即在门户域写入身份 Cookie：
      Nancal_Cam_SessionId = Base64(UTF-8(工号))，path=/，会话级
  → 点击业务系统菜单
  → 门户按该系统在花名册中的身份确定 Cookie 值（见 2.3），
    跨主机时后台隐藏 iframe 先在目标机补种 Cookie（不阻塞打开）
  → iframe 按菜单登记的完整 http 地址原样打开业务页面（不经门户拼接、不经过门户端口）
  → 页面内请求自动携带 Cookie
  → 业务系统后端拦截器解码 Cookie → 得到工号 → 查本系统用户 → 识别"当前用户"
```

各环节职责：

| 环节 | 负责 | 动作 |
|---|---|---|
| 写 Cookie | JUMP 前端 | 登录成功、刷新用户信息、切换业务系统时写入/改写 |
| 传 Cookie | 浏览器 | 同 hostname 自动携带（推荐部署形态）；跨机由 bridge 页补种 |
| 读 Cookie | 业务系统 | 拦截器解码 Base64 得工号，查本系统用户表放入上下文 |

## 2.2 身份 Cookie 定义

| 属性 | 取值 |
|---|---|
| Cookie 名称 | `Nancal_Cam_SessionId`（沿用 Camstar 体系原生 Cookie 名，现网 Camstar 类系统零改造即可识别） |
| Cookie 值 | `Base64(UTF-8(用户名))`，例：工号 `16358` 对应 `MTYzNTg=` |
| 路径 / 生命周期 | `path=/`，会话级（浏览器关闭即失效） |
| 写入时机 | 账密登录、社交登录、短信登录成功后，以及刷新用户信息时 |
| 登出清理 | 登出清除 Cookie 与 sessionStorage 备份，并清空 Camstar 页签保温池 |

Cookie 值自测（Git Bash）：`printf '16358' | base64` → `MTYzNTg=`

## 2.3 多系统身份区分：工号与「车间_工号」

同一 Cookie 名在不同业务系统中可能对应**不同的用户名**。区分依据是花名册登记：

**备注：针对camstar单用户访问多个系统时，需要车间_工号，camstar本身具备管理各车间MES账号的功能，各车间的MES账号本身在一个域控下，不能重名。**

**用户在JUMP的用户名是14059，如果想要访问多个车间的camstar MES时，那就需要在camstar系统注册时带上车间编号：4200_14059,3505_14059。**

| 花名册登记 | 该系统中的用户名 | Cookie 值（写入该系统前改写为） |
|---|---|---|
| 常规登记 | 工号（如 `10086`） | Base64(工号) |
| 勾选「拼接车间」（`username_with_workshop=1`） | `车间编号_工号`（如 `4200_10086`） | Base64(`4200_10086`) |

门户前端的处理规则：

- 登录后按「我的系统列表」注册各系统（clientId / subSystemId / origin / hostname）与用户名的映射表；
- **切换业务系统时**，立即按目标系统花名册身份重写本域 Cookie（进入 Camstar 且该人勾选了拼接车间时即变为 `车间_工号`）；
- **切回主系统时**，恢复为主登录工号；
- 精确映射未命中时按 URL origin → hostname 兜底；同一主机上多系统身份不同则置空防串号，未指定系统时只用主登录工号（禁止把「车间_工号」带到其他系统）；
- 跨主机种 Cookie 仍走后台补种（目标机需部署 bridge 页，见 2.4）。

人员推送侧与识别侧的对应约定：

- 花名册「注册」时可勾选**拼接车间**，注册到 Camstar 的用户名即 `车间编号_工号`；
- 门户刷卡登录 / 按用户名查询花名册时采用兼容查询：先按全名精确查，查不到再按后缀工号回查（须确认拼接标记且车间一致）。

## 2.4 部署形态与 Cookie 传递

浏览器按 hostname（而非端口）共享 Cookie，因此部署位置决定身份 Cookie 的传递方式：

| 形态 | 说明 | Cookie 传递方式 |
|---|---|---|
| 同主机不同端口 | 业务系统与门户同一台服务器 | 浏览器自动共享，**无任何额外工作（推荐主路径）** |
| 门户机 Nginx 反向代理（推荐） | 业务系统在其他机器，但经门户机 Nginx 反代为门户机同一 hostname 下的不同端口 | 跨机问题在部署层转化为"同机不同端口"，**业务系统无需部署 bridge 页** |

> 新接入系统优先采用「门户机 Nginx 反代」形态：菜单登记填反代地址、业务系统零额外部署。

## 2.5 Camstar 与其他业务系统的区别

Camstar 是现成商用系统，JUMP 对它的接入方式与自研系统（若依系 / 芋道系）显著不同：

| 对比维度 | Camstar / 现成系统（路径 C） | 自研系统（路径 A 若依 / 路径 B 芋道） |
|---|---|---|
| 业务系统侧改造量 | **零代码**：原生使用 `Nancal_Cam_SessionId` Cookie 识别用户 | 后端拦截器 + Security 放行 + 前端 3 处配置级改造 |
| 菜单登记方式 | 路由地址填完整 http 地址                                     | 同为**直开型**：路由地址填完整 http 地址；hash 路由的系统连同 `#` 一起登记，如 `http://…:8080/#/pageA` |
| 前端路由要求 | 页面须支持完整 URL 直达业务页 | history 或 hash 路由均可，能以完整 URL 打开业务页即可 |
| 人员接口接入 | **Camstar 会话型适配器**（apiType=camstar）：接口需要登录态，门户以「调用工号」经 SSO 登录激活会话，失败自动重登并重试一次；新增/修改请求体为 JSON 数组；删除人员连带删除域账号 | **HTTP 通用型适配器**（apiType=http）：纯配置驱动，无鉴权接口零代码接入；需特殊鉴权时门户侧开发专用适配器 |
| 用户名形态 | 可为 `车间编号_工号`（花名册勾选拼接车间），Cookie 值随系统切换改写 | 即工号 |
| 角色推送 | 对接 `updateRoleInfo`，门户侧角色名固定拼接为 `车间编号_角色名称` | 按通用接口契约推送 |
| iframe 体验增强 | 页签关闭进入**保温池**（上限 8 个，重开秒级恢复）；软超时 15 秒慢提示 / 硬超时 60 秒失败可重试 | 软超时 15 秒 / 硬超时 30 秒，经 about:blank 中转重挂载 |
| 部署 | 通常整站反代（如 4200/4306/4308/9011 端口）；人员接口目标单独登记（如「Camstar人员管理」192.168.240.125:8888） | 前端 + `/prod-api`（若依）或 `/admin-api`（芋道）分段反代，芋道需补 WebSocket 升级头 |

**自研系统"改代码适配门户"，Camstar"门户适配它"**——Cookie 名、会话接口、JSON 数组契约、页签保温等均是为 Camstar 零改造而定制的机制。

# 第三部分 门户管理员操作手册（引入业务系统与用户角色）

> 操作入口：浏览器访问门户地址（现网 `http://192.168.240.129:8088`），以管理员账号登录，左侧菜单「业务系统」分组下操作。各页面操作权限受 `sub-system:*` 权限点控制。

## 3.1 引入一个业务系统的完整流程

新业务系统接入按以下顺序操作（① ② 必做，③~⑥ 按需）：

```
① 登记业务系统（3.2）           —— 让业务系统出现在门户中
② 登记业务菜单（3.5）           —— 让业务页面可以打开
③ 配置人员接口（3.3）           —— 需要账号自动开通时
④ 维护车间对照 / 班组 / 岗位（3.4）—— 需要按部门带出车间、班组时
⑤ 登记业务角色并分配菜单权限（3.6）—— 需要控制谁能看哪些菜单时
⑥ 用户登记与注册推送（3.7）      —— 让具体人员可以使用该系统
```

## 3.2 业务系统登记

页面：`业务系统 → 系统管理`。

| 表单字段 | 填写说明 | 示例 |
|---|---|---|
| 系统编号（clientId） | 必填，字母开头，仅字母数字下划线中划线；非空即"门户业务系统"，留空则只是接口目标 | `mes4200` |
| 系统名称 | 必填 | 制造二部 MES |
| 系统图标 | 选填，图片上传 | — |
| 系统描述 | 选填 | — |
| 访问地址（systemUrl） | 系统入口地址（门户切换识别、错误书签纠偏等场景使用；业务菜单直开不经过它） | `http://192.168.240.129:4221` |
| 系统状态 | 开启 / 关闭；停用后该系统从用户门户中消失并使权限包失效 | 开启 |

## 3.3 人员接口接入（接口管理）

页面：`业务系统 → 接口管理`。左右布局：左侧接入系统树，右侧目录/接口面板。

**第一步：接入系统**

| 字段 | 说明 |
|---|---|
| 接入方式 | 选择 JUMP 业务系统（从已登记系统下拉）/ 添加其他系统（仅填名称，创建仅接口目标） |
| 适配器 | Camstar（会话型）/ HTTP（通用型） |
| 主机 | 接口基址，优先填门户机反代地址，如 `http://192.168.240.129:8888` |

**第二步：配置目录与叶子接口**。默认 Camstar 目录树含人员（查询 `getEmployeeInfo` / 新增修改 `addOrUpdateUser` / 删除 `deleteEmployeeInfo`）与角色（`getRoleInfo` / `updateRoleInfo` / `deleteRoleInfo`）接口，可按需增删。每个叶子接口独立配置：

| 字段 | 说明 |
|---|---|
| 接口名称 / 用途 | 用途取值：无 / 查询人员 / **新增人员（用户同步用）** / 修改人员 / 删除人员 / 角色查询 / 角色新增 / 角色删除 |
| 启用 | **「新增人员」叶子未启用的系统不会出现在注册推送的接口目标下拉中** |
| 方法 / 完整地址 | GET/POST/PUT/DELETE + 完整 URL（或相对主机的 path） |
| 会话 Cookie 开关 | 该接口是否携带会话（无状态接口关闭后不受会话过期影响） |
| 请求参数 / 响应 | JSON，用于在线测试 |

**第三步（Camstar 会话型）**：系统级会话鉴权配置——启用会话开关、登录地址（如 `http://…/Base/SSOLogin/SSOLoginIn`）、请求方法、**调用工号**（供 JUMP 作为会话账号）、Cookie 名（默认 `Nancal_Cam_SessionId`）。

**验证**（配置完成必做）：

- 每个叶子接口「测试」= 与真实调用一致地在线调试；
- 系统级「测试连接」= ping（执行 1 行分页查询，返回耗时与总人数）、「测试会话登录」= 验证 SSO 激活会话。

**字段改名**（对方参数名与 JUMP 标准名不一致时）：参数改名 `paramMapping`（如 `{"userCode":"empNo"}`）、成功判定 `responseMapping.successField/successValue`（默认 `code==200`）、失败信息字段（默认 `msg`）、列表/总数路径（默认 `data.list` / `data.total`）。配置后**业务系统无需改造字段命名**。

## 3.4 车间对照、班组、岗位

| 页面 | 字段 | 作用 |
|---|---|---|
| 车间对照 | JUMP 部门（必选）+ 车间编码（必填，如 4200）+ 车间名称 + 说明 | 创建用户登记花名册、注册推送时按用户部门自动带出车间编号；多个部门可映射同一车间 |
| 班组管理 | 车间编号（只读）+ 班组编码 + 班组名称 + 班组描述 + 班组长 | 花名册班组字段的下拉来源；支持导入 |
| 岗位管理 | 岗位名称 + 岗位编码 + 岗位顺序 + 岗位状态 | 花名册岗位（多选）的来源 |

推送时车间编号按五级优先级解析：花名册已有 → 注册弹窗显式指定 → 花名册系统的部门对照 → 接口目标系统的部门对照 → 推断（系统车间编码去重后唯一时直接采用，否则取系统名称中最后一组 ≥3 位数字，如 MES4200 取 4200）。解析失败该项标记失败，不中断批次。

## 3.5 业务菜单登记

页面：`业务系统 → 菜单管理`。左侧选择业务系统，右侧菜单树表。

**所有业务菜单统一为直开型**：路由地址登记**完整 http 地址**，门户 iframe 原样打开，不做任何拼接（组件路径不再使用）：

| 路由地址 | 组件路径 | 适用 |
|---|---|---|
| **完整 http 地址**，如 `http://192.168.240.129:4200/Process/ProcessManager/ProcessIndex`；hash 路由的系统连同 `#` 一起登记，如 `http://192.168.240.123:8080/#/intelligentCabinetMain` | 不再使用（留空） | 全部业务系统（Camstar、若依、芋道） |

登记要点：

- 登记页不支持冒号时（Vue Router 将冒号解析为动态参数），IP 与端口以「IP + `9` + 端口」编码，如 `192.168.240.12794200` 表示 `192.168.240.127:4200`，门户打开时自动解码还原；
- 菜单类型支持目录 / 菜单 / 按钮；一级菜单可选**菜单颜色**（子级继承）；支持上传**菜单说明书**（manualUrl）；
- 菜单数量多时支持**从 4200 的 `D2_SYS_MENU` 批量导入**，或使用「通用菜单」模板快速套用；
- 菜单/角色调整后如未即时生效，使用工具栏「**清门户缓存**」清除该系统的门户菜单 Redis 缓存。

## 3.6 业务角色管理

页面：`业务系统 → 角色管理`。左侧选择业务系统，右侧角色列表。

**角色登记**（新增 / 修改表单）：角色名称、角色标识、角色顺序、状态。角色只在 JUMP 本地维护。本页不再提供「同步到业务系统」「接口注册」列和「注册」操作，不从门户把角色定义或人员-角色关系推送到 Camstar。

**角色相关操作**：

| 操作 | 入口 | 说明 |
|---|---|---|
| 修改 | 行操作「修改」 | 修改角色名称、标识、顺序、状态 |
| 分配菜单权限 | 行操作「菜单权限」 | 勾选目录/页面/按钮，控制该角色在门户中可见的菜单；勾选页面时自动带上该页按钮；保存后自动刷新门户菜单缓存 |
| 快捷导航 | 行操作「快捷导航」 | 配置该角色的门户首页快捷导航卡片 |
| 导入 | 工具栏「导入」 | Excel 批量导入，可按角色标识更新 |
| 删除 | 行操作「删除」/ 工具栏「批量删除」 | 删除 JUMP 本地角色；已分配给用户的角色需先解除分配 |

说明：JUMP 角色只决定门户里能否看到菜单。Camstar 页面内的按钮权限、以及 Camstar 里的人员-角色关系，仍在 Camstar 侧维护，不由本页更改。

角色变更的联动：保存菜单权限后门户会 evict 相关用户的权限包并递增 RBAC 版本号，在线用户下次进入该系统时重新拉取菜单（必要时提示重新登录）。

## 3.7 用户管理（主用户 + 花名册 + 注册推送）

### 3.7.1 创建门户主用户（登记花名册）

页面：`系统管理 → 用户管理 → 新增用户`。

主用户表单字段：用户姓名（必填）、归属部门、用户名称（即工号，4-30 位字母数字）、用户密码、工号、域账号、刷卡卡号、ERP 账号（多选）、手机号码、性别、岗位、备注。

与花名册联动（仅新增时显示）：

1. 勾选「**同时登记业务系统用户**」，出现业务系统多选下拉（仅已绑定门户的系统；只有一个系统时自动选中）；
2. 提交后**同事务**写入所选系统的花名册（`employee_registered=0`），车间按部门对照自动带出；
3. 该步骤为**纯本地事务，不调用任何业务系统接口**——外部接口故障不会阻塞建用户。

> 同一工号已绑定其他主用户时拒绝并提示，需先在花名册解绑原记录。

### 3.7.2 注册推送（开通业务系统账号）

页面：`业务系统 → 用户管理`（花名册）。工具栏/行操作「**注册**」「**批量注册**」。

流程：选择花名册记录 → 选择**接口目标**（配置了「新增人员」接口且启用的系统）→ 可选车间（显式覆盖）与**拼接车间**（注册为 `车间编号_工号`，Camstar 用）→ 逐项调用对方新增人员接口：

- 注册状态已为 1 的自动跳过；成功置 1 并回填车间编号；**单项失败仅记录结果，不中断批次**，失败项可修正后重推；
- 推送字段：工号、姓名、车间编号、班组 code、域账号、ERP 工号（多个取第一个）、卡号。

> 对方系统已手工建人的记录，应手动将注册状态置 1 以避免重复推送。

### 3.7.3 花名册维护与角色分配

花名册新增/修改弹窗字段：业务系统（只读）、用户名、用户姓名、车间（下拉，联动班组）、班组、岗位（多选）、**角色（多选）**、**主页面**、状态、接口注册状态、备注。

- **分配角色**：花名册行操作「分配角色」，或直接在修改弹窗勾选；角色决定该用户在该系统中可见的菜单；
- **主页面（homeMenuId）**：必须先选角色，选项为所选角色可见的菜单树；角色变更时重载并清除不在树内的选择；
- 关联主用户：花名册创建时可绑定门户主用户；用户详情页「业务系统信息」区块亦可添加/编辑/删除业务系统关联。

| 路径 | 适用系统 | 改造量 |
|---|---|---|
| A | 若依（RuoYi）框架业务系统 | 后端 6 项 + 前端 3 处 |

## 4.2 通用接入前提（三类路径均须满足）

| # | 前提 | 核查方法 |
|---|---|---|
| 1 | **工号体系统一** | 解码 Cookie 得到的工号，本系统能检索到对应用户（用户表/工号字段/员工视图） |
| 2 | **通过 Cookie `Nancal_Cam_SessionId` 识别用户** | `curl -i "http://本机:端口/业务接口" -H "Cookie: Nancal_Cam_SessionId=MTYzNTg="` 能返回业务数据 |
| 3 | **允许被 iframe 嵌入** | 响应头无 `X-Frame-Options: DENY` / `CSP frame-ancestors 'none'`（框架 Security 配置与前置 nginx/IIS 均需检查） |
| 4 | **部署形态确认** | 首选门户机 Nginx 反代（同域免 bridge）；跨机直连需在站点根目录原样部署 `camstar-cookie-bridge.html` |

所有菜单均为直开型登记：页面须能以完整 URL 直达业务页——history 路由系统直接登记；hash 路由系统连同 `#` 一起登记完整地址。

## 4.3 自研系统改造要点（路径 A / B 摘要）

认证模型：**业务代码取"当前用户"只有一条权威通道——拦截器从 Cookie 解码工号后放入 ThreadLocal**；原登录机制（JWT/Bearer）仅用于通过 Security 过滤器与本系统独立登录场景。

| 改造项 | 若依（A） | 芋道（B） |
|---|---|---|
| 当前用户上下文 | 新建 `UserThreadLocal` | 拦截器内置 ThreadLocal |
| Cookie 拦截器 | 新建 `CamstarInfoInterceptor`：@Anonymous/白名单放行 → Cookie 解码工号 → 查用户 → ThreadLocal；无凭证返回 `{"code":4001}` | 同左（含 OPTIONS/注解放行、Bearer 回退） |
| Security 放行 | Controller 标注 `@Anonymous` + `frameOptions().disable()` | yaml `permit-all-urls` 放行需挂接的模块前缀（**Cookie 无法通过 Security，必须依赖此项**） |
| 注册拦截器 | `ResourcesConfig` 注册 `/**` | `WebMvcConfigurer` 注册 `/**` |
| 配置 | `camstar.whitelist / server-host-ip / dev-user-code` | 白名单在拦截器/配置类中维护 |
| 前端 3 处 | `withCredentials: true`；路由白名单免登（路由模式不限，hash 地址连同 `#` 登记完整地址） | `withCredentials: true`；路由白名单免登（同左） |
| 取当前用户 | `UserThreadLocal.get()`（操作日志等处兜底改造） | `CamstarInfoInterceptor.getUserName()`（注意 `"token"` 哨兵值分流） |

请求到达 Controller 前的关卡顺序（排查 401 按此检查）：**① CORS → ② Security 过滤器（验 token）→ ③ 拦截器（验 Cookie）**。

## 4.4 人员同步接口契约（路径 ② 摘要）

**HTTP 通用型（推荐，零代码接入）**：只需按约定提供 5 个接口，JUMP 侧纯配置调用——

| 用途 | 请求 | 响应（默认格式，可配） |
|---|---|---|
| 查询（分页） | `{"page":1,"rows":10,"userCode":"","userName":"","workshopCode":""}` 均可选 | `{"code":200,"data":{"total":100,"list":[…]}}` |
| **新增（必配）** | 员工字段 JSON | `{"code":200,"msg":"…"}` |
| 修改 | 同新增（upsert 语义） | 同上 |
| 删除 | `{"userCode":"16358"}` | 同上 |
| 班组下拉（可选） | `{"workshopCode":"4200"}` | 列表行字段 `teamCode`/`teamName` |

员工标准字段：`userCode`（工号）、`userName`、`workshopCode`（来自车间对照）、`teamCode`、`domainName`（域账号）、`erpNo`、`cardNo`。约定：成功判定默认 `code==200`；失败信息默认取 `msg`；空值参数不传输；字段名不一致由门户配置改名映射。

**Camstar 会话型**：需提供 SSO 登录接口（`GET /Base/SSOLogin/SSOLoginIn?token=Base64(工号)`）、四个人员接口（新增/修改请求体为 **JSON 数组**，查询响应为顶层 `rows`/`total`）、一个调用工号。

**特殊鉴权**（固定 token 头、签名等）：通用适配器不支持，需在 JUMP 侧开发专用适配器——实现 `SubSystemEmployeeApi` 六个能力（page/create/update/delete/teamCombo/ping），在 `SubSystemEmployeeApiFactory.createAdapter` 增加分支，配置页 api_type 填新类型。参照实现：`CamstarEmployeeApiAdapter`。

## 4.5 反向调用 JUMP（路径 ③ 摘要）

引入 SDK：`jonhonjump-framework/portal-subsystem-client`（Boot 2/3 双自动配置，配置前缀 `portal.subsystem.*`：clientId/clientSecret/apiUrl/portalUrl/read-mode 等）。

| 能力 | 端点 / Key | 鉴权 |
|---|---|---|
| 机端刷卡登录 | `POST /system/oauth2/subsystem/v1/card-login` | OAuth2 客户端密钥（Basic 或 body） |
| 权限信息拉取 | `POST /system/oauth2/subsystem/v1/permission-info` | 同上；返回角色、权限点、菜单树、RBAC 版本号 |
| 权限包直读 Redis | Key `portal:perm:context:{工号}:{clientId}` | Redis 直连（读模式 redis，miss 回退 HTTP） |
| 扩展缓存读写 | `/system/oauth2/subsystem/redis/v1/cache/{ns}/{key}` | scope + 命名空间白名单 |

一致性约定：门户在菜单/角色/花名册/用户/系统状态变更时 evict 权限包并递增 RBAC 版本号；业务系统比对本地版本，不一致或缓存 miss 时提示用户重新登录。
